## 主配置文件概述

`docker-compose.yml` 是 SmartAbp 低代码平台的核心部署配置文件，采用 Docker Compose 格式定义了整个应用的容器化部署方案。该文件通过声明式语法定义了多个相互依赖的服务，包括 Web 应用、数据库、缓存、搜索引擎、反向代理和监控系统等组件，实现了从开发到生产的全栈式容器化部署。

该配置文件遵循企业级最佳实践，通过 `version: '3.8'` 指定了 Docker Compose 的版本，确保了跨平台的兼容性和功能完整性。文件结构清晰地划分为 `services`、`networks` 和 `volumes` 三大顶级配置项，分别对应服务定义、网络配置和数据卷管理，形成了一个完整的微服务架构部署方案。

## 核心配置项解析

`docker-compose.yml` 文件的核心配置项包括 `version`、`services`、`networks` 和 `volumes`，这些配置项共同构成了容器化部署的基础框架。

`version` 配置项指定了 Docker Compose 文件的版本，当前使用 `3.8` 版本，这是 Docker Compose v3 系列中的稳定版本，支持大多数现代 Docker 功能，包括资源限制、健康检查和部署配置等高级特性。

`services` 配置项是文件的核心部分，定义了所有需要部署的容器化服务。每个服务都包含构建配置、容器名称、重启策略、端口映射、环境变量、依赖关系、网络配置和数据卷挂载等详细信息。服务之间通过 `depends_on` 实现启动顺序依赖，确保服务间的正确初始化顺序。

`networks` 配置项定义了容器间的通信网络。在本配置中，创建了一个名为 `smartabp-network` 的桥接网络，所有服务都连接到此网络，实现了容器间的内部通信。该网络配置了 `172.20.0.0/16` 的子网范围，为容器分配了独立的 IP 地址空间。

`volumes` 配置项定义了持久化数据卷，用于存储数据库数据、日志文件和上传文件等需要持久化的数据。每个数据卷都使用 `local` 驱动，确保数据存储在宿主机的本地文件系统中，即使容器被删除，数据也能得到保留。

## 前端服务配置

前端服务 `smartabp-web` 的配置体现了现代 Web 应用的容器化部署最佳实践。该服务通过 `build` 指令从项目根目录的 `Dockerfile` 构建镜像，实现了前后端一体化的构建流程。容器名称设置为 `smartabp-lowcode-engine`，便于在 Docker 环境中识别和管理。

端口映射配置将容器内的 80 端口映射到宿主机的 8080 端口，实现了外部访问。环境变量配置中，`ASPNETCORE_ENVIRONMENT=Production` 指定了运行环境为生产环境，影响了应用的行为模式。数据库连接字符串通过环境变量注入，确保了配置的灵活性和安全性。

服务依赖关系通过 `depends_on` 指令明确声明，前端服务依赖于 `sqlserver`、`redis` 和 `elasticsearch` 三个后端服务，确保在这些依赖服务启动并准备好后再启动前端服务。网络配置将服务连接到 `smartabp-network` 网络，实现了与其他服务的内部通信。

数据卷挂载配置了两个持久化卷：`smartabp-logs` 用于存储应用日志，`smartabp-uploads` 用于存储用户上传的文件。这种分离式存储设计提高了数据管理的灵活性和安全性。

## 后端服务配置

后端服务配置涵盖了数据库、缓存和搜索引擎等关键基础设施组件，体现了企业级应用的完整技术栈。

SQL Server 数据库服务 `sqlserver` 使用官方镜像 `mcr.microsoft.com/mssql/server:2022-latest`，容器名称为 `smartabp-sqlserver`。通过环境变量 `SA_PASSWORD` 设置了管理员密码，`ACCEPT_EULA=Y` 接受了许可协议。端口映射将容器的 1433 端口暴露给宿主机，便于外部数据库工具连接。数据卷 `sqlserver-data` 挂载到 `/var/opt/mssql`，确保了数据库文件的持久化存储。

Redis 缓存服务 `redis` 使用 `redis:7-alpine` 镜像，容器名称为 `smartabp-redis`。通过 `command` 指令设置了密码保护，增强了安全性。端口映射将 6379 端口暴露给宿主机，数据卷 `redis-data` 挂载到 `/data` 目录，实现了数据持久化。

Elasticsearch 搜索引擎服务 `elasticsearch` 使用 `docker.elastic.co/elasticsearch/elasticsearch:8.8.0` 镜像，容器名称为 `smartabp-elasticsearch`。配置中禁用了安全功能 `xpack.security.enabled=false`，并设置了 JVM 内存限制。`ulimits` 配置调整了内存锁定和文件描述符限制，满足了 Elasticsearch 的性能要求。数据卷 `elasticsearch-data` 挂载到 `/usr/share/elasticsearch/data`，确保了索引数据的持久化。

## 数据库服务配置

数据库服务配置不仅包括了基本的 SQL Server 部署，还通过 `docker-compose.databases.yml` 文件提供了多数据库支持的灵活配置方案。

`docker-compose.databases.yml` 文件定义了三种主流数据库的部署配置：PostgreSQL、MySQL 和 SQL Server。每种数据库都有独立的容器配置，包括不同的镜像、端口映射、环境变量和初始化脚本。例如，PostgreSQL 服务使用 `postgres:15-alpine` 镜像，映射到宿主机的 5432 端口；MySQL 服务使用 `mysql:8.0` 镜像，映射到 3306 端口；SQL Server 服务使用微软官方镜像，映射到 1433 端口。

每种数据库都配置了相应的管理工具容器，如 `pgadmin` 用于 PostgreSQL 管理，`phpmyadmin` 用于 MySQL 管理。这些管理工具容器通过 `depends_on` 依赖于对应的数据库服务，并配置了相应的环境变量，实现了开箱即用的数据库管理体验。

健康检查配置是数据库服务的重要组成部分，每种数据库都定义了特定的健康检查命令。例如，PostgreSQL 使用 `pg_isready` 命令检查服务状态，MySQL 使用 `mysqladmin ping` 命令，SQL Server 使用 `sqlcmd` 命令。这些健康检查确保了容器编排系统能够准确判断服务的健康状态。

## 环境变量管理

环境变量管理是 `docker-compose.yml` 配置文件的关键安全特性，通过环境变量实现了配置与代码的分离，提高了部署的灵活性和安全性。

在 `docker-compose.yml` 文件中，环境变量通过 `environment` 指令注入到容器中。例如，前端服务配置了 `ASPNETCORE_ENVIRONMENT`、`ConnectionStrings__Default` 和 `ElasticSearch__Url` 等环境变量，这些变量直接影响了应用的运行时行为。数据库服务通过环境变量设置管理员密码和许可协议，避免了在配置文件中硬编码敏感信息。

`docker-compose.production.yml` 文件进一步强化了环境变量管理的安全性，使用了 `${VARIABLE_NAME:?error message}` 语法，确保了关键环境变量的强制性。例如，`DB_PASSWORD` 和 `REDIS_PASSWORD` 等敏感变量在缺失时会直接导致容器启动失败，防止了因配置缺失导致的安全漏洞。

环境变量的命名采用了双下划线 `__` 分隔的层次结构，这与 .NET 配置系统兼容，能够自动映射到应用的配置层次结构中。例如，`ConnectionStrings__Default` 会自动映射到配置的 `ConnectionStrings:Default` 节点，实现了无缝的配置集成。

## 网络与卷配置

网络与卷配置是容器化部署的基础，确保了服务间的通信和数据的持久化。

`networks` 配置项定义了 `smartabp-network` 网络，采用 `bridge` 驱动模式，这是 Docker 默认的网络模式，适用于单主机上的容器间通信。网络配置了 `172.20.0.0/16` 的子网范围，为容器分配了充足的 IP 地址空间。这种独立的网络命名空间确保了容器间的通信隔离，提高了安全性。

`volumes` 配置项定义了多个数据卷，包括 `sqlserver-data`、`redis-data`、`elasticsearch-data`、`prometheus-data`、`grafana-data`、`smartabp-logs` 和 `smartabp-uploads`。每个数据卷都使用 `local` 驱动，将容器内的目录挂载到宿主机的本地文件系统中。这种持久化存储设计确保了即使容器被删除或重建，重要数据也不会丢失。

数据卷的命名遵循了清晰的命名规范，前缀 `smartabp-` 标识了所属项目，后缀 `-data`、`-logs` 或 `-uploads` 明确了数据类型。这种命名约定提高了配置的可读性和可维护性，便于运维人员快速识别和管理数据卷。

## 配置文件分层策略

项目采用了多层配置文件策略，通过不同的 `docker-compose` 文件实现了开发、生产和数据库专用环境的分离。

`docker-compose.yml` 是基础配置文件，定义了完整的生产环境部署方案。`docker-compose.dev.yml` 是开发环境覆盖文件，通过不同的端口映射（如 1434、6380、9201）避免了与生产环境的端口冲突，同时增加了开发专用工具如 `mailhog-dev`、`minio-dev` 和 `jaeger-dev`。

`docker-compose.production.yml` 是生产环境专用配置文件，采用了更严格的资源限制和安全配置。该文件使用了 `deploy` 指令定义了资源限制和预留，如 `cpus` 和 `memory` 的限制，确保了生产环境的资源稳定。`replicas: 3` 配置实现了应用的多实例部署，提高了可用性和负载能力。

`docker-compose.databases.yml` 是数据库专用配置文件，提供了多数据库支持的灵活部署方案。这种分层策略允许开发团队根据不同的需求选择合适的配置组合，如 `docker-compose -f docker-compose.yml -f docker-compose.dev.yml up` 可以同时应用基础配置和开发覆盖配置。
