# 任务分级流程 - 弹性执行机制

## 📋 概览

**核心理念**: 根据任务复杂度选择流程,简单任务快速响应,复杂任务深入分析

**使用场景**: 所有编程任务开始前必须先判断级别

**阅读时间**: 5分钟

---

## 🎯 任务级别判断标准

| 级别 | 代码量 | 复杂度 | 典型场景 | 时间 | 流程 |
|------|--------|--------|----------|------|------|
| **Level 1** | <20行 | 微小修改 | 变量名、注释、样式 | <2分钟 | 3步 |
| **Level 2** | 20-200行 | 中等任务 | 新组件、修BUG | 5-15分钟 | 6步 |
| **Level 3** | >200行 | 重大任务 | 新功能、架构调整 | 15-60分钟 | 4-8阶段 |

---

## 📊 快速决策流程

```
接到任务
  ↓
预估代码量?
  ↓
  ├─ <20行 → Level 1(立即执行)
  │
  ├─ 20-200行 → Level 2(简要分析)
  │
  └─ >200行 → Level 3
              ↓
              熟悉项目?
              ├─ 是(最近10分钟内学习过)
              │  └─ 模式1: 四阶段核心流程
              │     详见: 03_Level3_模式1_四阶段.mdc
              │
              └─ 否(新会话/新模块)
                 └─ 模式2: 完整八阶段流程
                    详见: 04_Level3_模式2_完整八阶段.mdc
```

## 🔧 Level 1: 微小任务(快速响应)

### 适用场景

```yaml
典型任务:
  - 修改变量名
  - 添加/修改注释
  - 调整CSS样式
  - 修复明显的小BUG
  - 简单配置调整

特征:
  - 单一修改
  - 无架构影响
  - 无业务逻辑变更
  - <20行代码
```

### 执行流程(3步,<2分钟)

```markdown
### 步骤1: 快速理解(30秒)
- [ ] 用户想要什么?
- [ ] 修改的影响范围?
- [ ] 是否确实是Level 1任务?

### 步骤2: 直接修改(1分钟)
- [ ] 遵循代码标准
- [ ] 保持类型安全
- [ ] 使用search_replace工具

### 步骤3: 简单验证(30秒)
- [ ] TypeScript检查: npm run type-check
- [ ] 确认修改正确
- [ ] 报告完成
```

### 不需要的事项

```yaml
❌ 不需要:
  - 业界搜索
  - 深度分析
  - 用户确认方案
  - 完整测试报告
  - Git同步(除非用户要求)
  - 质量门禁(但要通过基本检查)
```

### 示例

**任务**: "将变量userName改为userAccount"

```markdown
执行记录:
- [x] 步骤1: 快速理解 ✅
      - 修改变量名: userName → userAccount
      - 影响范围: 当前文件
      - 确认Level 1 ✅

- [x] 步骤2: 直接修改 ✅
      - 使用search_replace精确替换
      - 保持类型定义一致
      - 更新相关注释

- [x] 步骤3: 简单验证 ✅
      - TypeScript编译: 0错误 ✅
      - 功能正常: 手动验证 ✅

✅ 完成! 总耗时: 1.5分钟
```

## 🛠️ Level 2: 中等任务(简要分析)

### 适用场景

```yaml
典型任务:
  - 添加新组件(Vue/React组件)
  - 修复复杂BUG
  - 功能优化
  - 小范围重构
  - API接口调整

特征:
  - 需要分析思考
  - 有一定复杂度
  - 局部影响
  - 20-200行代码
```

### 执行流程(6步,5-15分钟)

```markdown
### 步骤1: 理解需求(2分钟)
- [ ] 用户想要什么?
- [ ] 为什么需要?
- [ ] 成功标准是什么?
- [ ] 确认是Level 2任务

### 步骤2: 检索现有实现-DRY原则(2分钟)
- [ ] 搜索相似组件/函数
- [ ] 检查是否可复用
- [ ] 参考现有模式
- [ ] 命令: search_codebase / search_symbol

### 步骤3: 简要技术分析-8节点(3分钟)
- [ ] 节点1: 用户想实现什么?(表面需求)
- [ ] 节点2: 为什么需要?(业务价值)
- [ ] 节点3: 技术方案选择
- [ ] 节点4: 实现路径规划
- [ ] 节点5: 潜在问题识别
- [ ] 节点6: 参考业界实践(可选1-2个搜索)
- [ ] 节点7: 性能考虑
- [ ] 节点8: 架构一致性检查

### 步骤4: 编码实现(5-8分钟)
- [ ] 遵循代码标准
- [ ] 完整的TypeScript类型定义
- [ ] 适当的错误处理
- [ ] 清晰的注释
- [ ] 见名知义的命名

### 步骤5: 质量检查(2分钟)
- [ ] TypeScript: npm run type-check => 0错误
- [ ] ESLint: npm run lint => 0错误0警告
- [ ] 架构合规: 无相对路径、无@别名违规(如涉及packages)
- [ ] 代码重复: 无重复组件/函数名

### 步骤6: 功能验证(1分钟)
- [ ] 手动测试主要功能
- [ ] 确认符合预期
- [ ] 报告完成
```

### 可选项

```yaml
业界搜索: 1-2个关键问题(可选,视情况而定)
用户确认: 复杂方案时建议确认
Git同步: 可选(除非接近300行)
```

### 示例

**任务**: "添加一个用户列表展示组件"

```markdown
执行记录:
- [x] 步骤1: 理解需求 ✅
      - 需要: 展示用户列表,支持分页
      - 原因: 用户管理功能需要
      - 成功: 显示用户信息+分页工作

- [x] 步骤2: 检索现有实现 ✅
      - 搜索: search_codebase("用户列表")
      - 发现: src/views/admin/UserList.vue (可参考)
      - 复用: 分页组件、表格样式

- [x] 步骤3: 简要技术分析 ✅
      - 技术: Vue 3 + Composition API
      - 路径: 使用ElTable + 分页组件
      - 问题: 大数据量性能
      - 方案: 虚拟滚动(如超过1000条)

- [x] 步骤4: 编码实现 ✅
      - 文件: UserListComponent.vue
      - 代码量: 156行
      - 类型: 100%类型安全
      - 复用: BasePagination组件

- [x] 步骤5: 质量检查 ✅
      - TypeScript: 0错误 ✅
      - ESLint: 0错误0警告 ✅
      - 架构: 合规 ✅

- [x] 步骤6: 功能验证 ✅
      - 测试: 显示10条数据 ✅
      - 测试: 分页切换正常 ✅
      - 测试: 响应式布局 ✅

✅ 完成! 总耗时: 12分钟, 代码质量: 96分
```

## 🚀 Level 3: 重大任务(深度分析)

### 适用场景

```yaml
典型任务:
  - 新功能模块(>200行)
  - 架构调整
  - 大规模重构
  - 复杂业务逻辑
  - 跨模块功能

特征:
  - 高复杂度
  - 全局影响
  - 需深度分析
  - >200行代码
  - 涉及多个文件
```

### 两种执行模式

#### 模式选择决策树

```
Level 3任务
  ↓
最近10分钟内学习过项目?
  ↓
  ├─ 是(已熟悉架构、代码库、模板)
  │  └─ 模式1: 四阶段核心流程
  │     - 时间: 15-30分钟
  │     - 阶段: A/B/门禁/Git
  │     - 详见: 03_Level3_模式1_四阶段.mdc
  │
  └─ 否(新会话/新模块/陌生项目)
     └─ 模式2: 完整八阶段流程
        - 时间: 30-60分钟
        - 阶段: 0-8(包含完整学习)
        - 详见: 04_Level3_模式2_完整八阶段.md
```

### 模式1: 四阶段核心流程(熟悉项目)

**适用条件**:
- ✅ AI最近10分钟内执行过阶段0-2(项目学习)
- ✅ 任务是延续性开发
- ✅ 已知道代码结构和模板位置
- ✅ 用户说"继续开发"、"添加功能"

**流程概览**:
```
阶段A: 编程前深度分析(15节点) → 5分钟
阶段B: 精心编程(业界顶级) → 10-20分钟
质量门禁: 五关强制检查 → 3-5分钟
Git同步: 三层降级策略 → 2分钟
```

**详见**: [03_Level3_模式1_四阶段.md](03_Level3_模式1_四阶段.md)

---

### 模式2: 完整八阶段流程(新项目)

**适用条件**:
- ✅ 新会话开始,AI不了解项目
- ✅ 涉及新模块、新技术栈
- ✅ 需要学习现有代码和模板
- ✅ 用户说"开始一个新功能"、"重构模块"

**流程概览**:
```
阶段0: 规则与架构理解 → 5分钟
阶段1: 架构识别 → 5分钟
阶段2: 功能学习与去重(DRY) → 5分钟
阶段3: 编程前深度分析(15节点) → 5分钟
阶段4: 用户确认 → 1分钟
阶段5: 精心编程(业界顶级) → 15-30分钟
阶段6: 质量门禁(五关) → 5分钟
阶段7: Git版本管理 → 2分钟
阶段8: 自动推进机制 → <1分钟
```

**详见**: [04_Level3_模式2_完整八阶段.md](04_Level3_模式2_完整八阶段.md)

## ⚠️ 常见误判与纠正

### 误判1: 将Level 2当作Level 1

```yaml
症状:
  - AI直接修改,跳过分析
  - 未检索现有实现
  - 代码重复

纠正:
  - 任何新增功能都至少是Level 2
  - 必须执行DRY检查
  - 必须简要分析
```

### 误判2: 将Level 3当作Level 2

```yaml
症状:
  - 代码量超过200行仍用Level 2流程
  - 未执行深度分析
  - 未通过质量门禁

纠正:
  - 超过200行强制升级到Level 3
  - 必须执行15节点深度分析
  - 必须通过五关质量门禁
```

### 误判3: 模式选择错误

```yaml
症状:
  - 新会话使用模式1(缺少项目学习)
  - 延续开发使用模式2(浪费时间)

纠正:
  - 新会话/新模块 → 模式2
  - 延续开发(10分钟内) → 模式1
  - 不确定时选择模式2(更安全)
```
