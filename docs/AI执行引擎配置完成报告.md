## 🎯 300行增量编程机制详解

### 核心目标

避免一次性编写大量代码导致：
- ❌ 超时
- ❌ 质量下降
- ❌ 难以调试

### 四个关键节点

```yaml
节点1 (100行): 快速自检
  触发: 累计编写达到100行代码
  动作:
    - 快速TypeScript类型检查
    - 核心逻辑自查
    - 关键注释补充
  结果: 继续编程（不停止）

节点2 (200行): 中等强度自检
  触发: 累计编写达到200行代码
  动作:
    - TypeScript类型检查
    - ESLint快速检查
    - 架构合规性自查
    - 功能完整性评估（50%进度）
  结果: 继续编程（不停止）

节点3 (280行): 准备收尾
  触发: 累计编写达到280行代码
  动作:
    - 黄色警告提示
    - 评估剩余工作量
  决策:
    - 剩余<20行 → 快速收尾
    - 剩余>20行 → 立即触发质量门禁

节点4 (300行): 强制停止
  触发: 累计编写达到300行代码
  动作:
    - 🛑 强制停止编程
    - 触发完整质量门禁
    - Git同步（如果质量通过）
    - 生成进度报告
    - 提供下一步方案（A/B/C）
  结果: 等待用户选择
```

### 代码行数计算规则

```yaml
计入:
  ✅ TypeScript/JavaScript/Vue/C# 实际代码行
  ✅ 有效注释行（非空注释）

不计入:
  ❌ 空行
  ❌ 纯装饰性注释（━━━━━━）
  ❌ import/export 语句

特殊情况:
  - 修改现有文件: 只计算新增行数
  - 删除代码: 不计入行数
  - 重构代码: 按净增行数计算
```

### 超过300行的处理流程

**示例：功能需要400行代码**

```yaml
第1轮（0-300行）:
  1. 编写核心功能（200行）
  2. 编写基础UI（80行）
  3. 编写类型定义（20行）
  4. 达到300行 → 触发质量门禁
  5. 质量通过 → Git同步
  6. 生成进度报告

暂停并向用户汇报:
  "✅ 第1轮完成（300/400行，75%）
   已完成: 核心功能 + 基础UI + 类型定义
   质量检查: 通过
   下一步: 
     A. 继续完成剩余100行（推荐）
     B. 暂停，让用户验证当前进度
     C. 调整方案"

第2轮（300-400行）:
  1. 编写高级UI（60行）
  2. 编写错误处理（30行）
  3. 完善注释和文档（10行）
  4. 达到400行 → 功能完成
  5. 触发最终质量门禁
  6. Git同步
```

## 🛡️ AI守护机制详解

### 六大守护检查点

```yaml
1. 任务理解守护
   时机: 收到用户需求后立即执行
   目的: 确保理解用户真实意图和成功标准

2. 架构合规守护
   时机: 每次引用其他模块/package时
   目的: 防止违反架构三大铁律

3. 类型安全守护
   时机: 每次编写函数/接口时
   目的: 确保100%类型安全，禁止any

4. 功能完整性守护
   时机: 每个功能模块完成后
   目的: 防止花瓶式实现（空方法、Mock数据）

5. 代码质量守护
   时机: 每100行代码
   目的: 保证代码清晰、有注释、有错误处理

6. 进度跟踪守护
   时机: 每个阶段完成后
   目的: 确保不偏离目标，及时向用户汇报
```
