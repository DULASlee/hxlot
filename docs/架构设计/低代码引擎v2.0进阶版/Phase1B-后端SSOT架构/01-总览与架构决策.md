## 🎯 Phase 1B 核心目标

**从前端统一元数据模型（unified-schema.ts）转向后端SSOT架构**

### 旧架构问题（已废弃）

```typescript
// ❌ 前端统一元数据模型（已废弃）
// src/SmartAbp.Vue/packages/lowcode-shared/src/types/unified-schema.ts

export interface UnifiedEntityDefinition {
  name: string
  displayName: string
  fields: UnifiedEntityField[]
  // ... 数千行类型定义
}

问题：
  ❌ 前后端双重维护（Backend Domain + Frontend unified-schema）
  ❌ 手动同步类型（ConvertUnified() 映射函数）
  ❌ 类型不一致风险（后端改了前端忘记同步）
  ❌ 不是真正的SSOT（Single Source of Truth）
```

### 新架构（已实现）✅

```yaml
后端SSOT架构：

Domain层（唯一真实源）:
  - 实体Entity: EntityDefinition, EntityField, EntityRelation
  - 配置类Config: PropertyUIConfig, PageConfigDto, ValidationRuleConfig
  - 存储: PostgreSQL/MySQL数据库 + JSON字段
  - 特点: 唯一、完整、权威的元数据定义

Application.Contracts层（API契约）:
  - DTO: EntityDefinitionDto, EntityFieldDto
  - 配置引用: public PropertyUIConfig? UIConfig { get; set; }
  - 特点: 遵循ABP标准，引用Domain配置类型

Swagger/NSwag链路:
  - Swagger: 扫描Domain层类型 → 生成OpenAPI JSON
  - NSwag: 读取OpenAPI JSON → 生成TypeScript类型
  - 前端: 直接使用生成的TypeScript类型（零手动维护）

优势：
  ✅ 真正的SSOT：Domain层是唯一真实源
  ✅ 自动类型同步：后端改了，前端自动同步（通过NSwag）
  ✅ 零手动映射：删除ConvertUnified()映射函数
  ✅ 100%类型安全：TypeScript类型与后端完全一致
```

## 🔥 关键架构决策

### 决策1: 废除前端统一元数据模型

**决策时间**: Phase 1B开始
**决策者**: AI架构师提议 + 首席架构师确认
**理由**:

1. **重复维护成本高**：前端`unified-schema.ts`与后端`Domain`层重复定义
2. **手动同步易出错**：`ConvertUnified()`映射函数容易遗漏字段
3. **不符合SSOT原则**：两个"真实源"导致数据不一致
4. **阻碍迭代速度**：后端改字段，前端要手动同步，效率低

**结果**:
- ✅ 删除`unified-schema.ts`（将在Phase 1D执行）
- ✅ 删除`ConvertUnified()`映射函数
- ✅ 前端直接使用NSwag生成的类型

---

### 决策2: Domain层作为SSOT的同时保持ABP标准模式

**决策时间**: Phase 1B中期
**决策者**: 首席架构师最终决定

**AI最初提案**: 彻底SSOT，删除所有DTO，直接暴露Domain实体
```typescript
// AI最初提案（被否决）
export class EntityDefinitionAppService {
  // ❌ 直接返回Domain实体
  public async Task<EntityDefinition> GetAsync(Guid id)
}
```

**首席架构师决策**: 遵循ABP标准模式，保持DTO作为API契约
```csharp
// ✅ 最终方案（已采纳）
public class EntityDefinitionAppService {
  // 返回DTO（API契约）
  public async Task<EntityDefinitionDto> GetAsync(Guid id)
}

public class EntityDefinitionDto {
  // 基础字段
  public string Name { get; set; }
  public string DisplayName { get; set; }

  // 引用Domain配置类型（SSOT）
  public PageConfigDto? PageConfig { get; set; }  // ← Domain层类型
}
```

**理由**:
1. ✅ **ABP兼容性**: 符合ABP框架的标准实践
2. ✅ **API版本控制**: DTO作为契约，便于版本管理
3. ✅ **向后兼容**: 修改Domain实体不会破坏API契约
4. ✅ **职责分离**: Domain负责业务逻辑，DTO负责数据传输
5. ✅ **SSOT保证**: DTO引用Domain配置类型，配置定义仍是唯一真实源

**架构图**:
```
┌─────────────────────────────────────────────────────────┐
│                   前端TypeScript                         │
│   使用NSwag生成的类型（自动同步）                         │
└─────────────────────┬───────────────────────────────────┘
                      │ NSwag生成
                      ▼
┌─────────────────────────────────────────────────────────┐

│   扫描Domain层类型 + Application.Contracts DTO           │
└─────────────────────┬───────────────────────────────────┘
                      │ Swagger扫描
                      ▼
┌─────────────────────────────────────────────────────────┐
│          Application.Contracts层（API契约）              │
│   EntityDefinitionDto {                                 │
│     Name: string                    ← 基础字段           │
│     DisplayName: string             ← 基础字段           │
│     PageConfig: PageConfigDto?      ← 引用Domain层       │
│   }                                                      │
└─────────────────────┬───────────────────────────────────┘
                      │ 引用
                      ▼
┌─────────────────────────────────────────────────────────┐
│              Domain层（SSOT - 唯一真实源）               │
│   EntityDefinition {                                    │
│     Name: string                                        │

│     Fields: List<EntityField>                           │

│   }                                                      │

                      │
                      ▼
```

### 决策3: Application.Contracts引用Domain层

**决策时间**: Phase 1B执行
**技术挑战**: ABP框架通常是`Application.Contracts`不依赖`Domain`

**解决方案**: 添加项目引用
```xml
<!-- src/SmartAbp.Application.Contracts/SmartAbp.Application.Contracts.csproj -->
<ItemGroup>
  <ProjectReference Include="..\SmartAbp.Domain.Shared\SmartAbp.Domain.Shared.csproj" />
  <!-- Phase 1B架构修正：Application.Contracts引用Domain层完整配置类型 -->
  <ProjectReference Include="..\SmartAbp.Domain\SmartAbp.Domain.csproj" />
</ItemGroup>
```

**影响评估**:
- ✅ **正面**: DTO可以引用Domain配置类型，实现配置的SSOT
- ⚠️ **注意**: 打破ABP惯例，需要确保不引入循环依赖
- ✅ **验证**: 编译通过，无循环依赖警告

## 🎯 架构原则

### 1. SSOT原则（Single Source of Truth）

**定义**: 每个数据元素只在一个地方定义

**实施**:
- ✅ Domain层是元数据的唯一真实源
- ✅ Application.Contracts DTO引用Domain配置类型（不重复定义）
- ✅ 前端TypeScript类型由NSwag自动生成（不手动定义）

### 2. DRY原则（Don't Repeat Yourself）

**定义**: 不要重复定义

**实施**:
- ✅ 删除unified-schema.ts中与Domain重复的类型定义
- ✅ 删除EntityUIConfigDto等简化DTO
- ✅ 删除ConvertUnified()手动映射函数

### 3. ABP兼容原则

**定义**: 遵循ABP框架标准实践

**实施**:
- ✅ 保持Application.Contracts DTO作为API契约
- ✅ AppService返回DTO而非Domain实体
- ✅ 使用AutoMapper进行Entity ↔ DTO映射
