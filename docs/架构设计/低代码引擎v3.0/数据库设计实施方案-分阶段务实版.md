### 1.2 改进建议分析（务实评估）

#### **建议1：添加配置快照表（LC_ConfigSnapshots）**

```yaml
专家建议:
  - 添加配置变更历史
  - 支持审计和回滚

务实评估:
  ❓ 必要性: 中等（现阶段可以依赖Git）
  ❓ 复杂度: 低（1张表，简单查询）
  ❓ 收益: 后期有价值（回滚、审计）

决策: 🟡 Phase 2实施（非紧急）
  理由:
    - Git已经提供版本控制
    - 配置还没复杂到需要专门的快照机制
    - 后期如果需要，很容易添加
```

#### **建议2：增强索引策略（JSON字段GIN索引）**

```yaml
专家建议:
  - PostgreSQL使用GIN索引
  - SQL Server使用计算列+索引

务实评估:
  ❓ 必要性: 低（数据量小时不需要）
  ❓ 复杂度: 中等（需要数据库特定语法）
  ❓ 收益: 数据量>10万条时才有明显效果

决策: 🟢 Phase 3实施（性能优化阶段）
  理由:
    - 初期数据量小（<1000个实体），B-Tree索引足够
    - JSON字段查询频率低（主要是等值查询EntityId）
    - 过早优化是万恶之源
```

#### **建议3：强类型DTO约束（PropertyUIConfigDto）**

```yaml
专家建议:
  - 为JSON字段创建强类型DTO
  - 添加JSON Schema验证

务实评估:
  ✅ 必要性: 高（类型安全，防止JSON格式错误）
  ✅ 复杂度: 低（C#类定义，简单）
  ✅ 收益: 立即见效（编译时检查，减少运行时错误）

决策: 🔴 Phase 1立即实施（核心功能）
  理由:
    - TypeScript和C#都需要强类型
    - 防止前后端JSON格式不一致
    - EF Core值转换器自动序列化/反序列化
```

#### **建议4：配置验证服务（PageConfigValidator）**

```yaml
专家建议:

  ✅ 复杂度: 中等（需要编写验证逻辑）
```

### 2.3 Phase 3：性能优化（性能瓶颈时实施）

**目标：应对大数据量，提升查询性能**

#### **性能优化措施**
```sql
-- 1. PostgreSQL GIN索引（数据量>10万条时）
CREATE INDEX IX_LC_Properties_UIConfig_GIN
ON LC_Properties USING GIN (UIConfig jsonb_path_ops);

-- 2. SQL Server计算列+索引
ALTER TABLE LC_Properties
ADD UIControlType AS JSON_VALUE(UIConfig, '$.controlType');

CREATE INDEX IX_LC_Properties_UIControlType
ON LC_Properties(UIControlType);

-- 3. 缓存策略
// Redis缓存PageConfig（热数据）
var pageConfig = await _cache.GetOrSetAsync(
    $"PageConfig:{entityId}:{pageType}",
    () => _repo.GetPageConfig(entityId, pageType),
    TimeSpan.FromHours(1)
);
```
