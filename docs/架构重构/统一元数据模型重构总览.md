## 🎯 重构愿景

### 核心目标
建立基于JSON Schema的统一元数据模型，实现前后端元数据的高度一致性，支持企业级低代码引擎和.NET Aspire微服务编排的完美集成。

### 战略意义
- **技术统一**: 前后端使用统一的Schema定义，消除二义性
- **类型安全**: 自动生成TypeScript和C#类型，实现编译时类型检查
- **架构演进**: 建立Schema版本管理机制，支持系统长期演进
- **效率提升**: 元数据驱动代码生成，开发效率提升50%+
- **质量保障**: Schema验证+类型安全+自动化测试，质量评分≥95分

## 💎 核心技术决策

### 决策1: 选择JSON Schema作为统一Schema规范
**理由**:
- 业界标准，工具链成熟（NJsonSchema、quicktype）
- 支持完整的类型系统和验证规则
- 支持Schema版本控制和演进
- 前后端工具都有良好支持

**替代方案对比**:
| 方案 | 优点 | 缺点 | 评分 |
|------|------|------|------|
| JSON Schema | 业界标准、工具成熟 | 学习曲线 | 95分 ✅ |
| Protocol Buffers | 性能优秀 | 不适合JSON API | 80分 |
| GraphQL Schema | 类型安全 | 仅适用GraphQL | 75分 |
| 自定义Schema | 灵活性高 | 无生态支持 | 60分 |

---

### 决策2: 采用Schema-First设计模式
**理由**:
- Schema是唯一真实来源（Single Source of Truth）
- 前后端类型自动生成，减少手工维护
- 支持API契约先行，前后端并行开发
- 符合GraphQL、OpenAPI等顶尖框架的设计理念

**实施方式**:
```
1. 定义JSON Schema
2. 自动生成C# DTO和TypeScript接口
3. 基于生成的类型开发业务逻辑
4. Schema变更 → 重新生成 → 编译检查 → 发现不兼容
```

---

### 决策3: 建立Schema版本管理机制
**理由**:
- 支持系统长期演进
- 向后兼容性保证
- 渐进式迁移能力

**版本策略**:
- **主版本**（1.x.x → 2.x.x）：破坏性变更
- **次版本**（x.1.x → x.2.x）：新增字段（向后兼容）
- **修订版本**（x.x.1 → x.x.2）：Bug修复

### 3. 验证器实现

**后端（C# - NJsonSchema）**:
```csharp
public class SchemaValidator : ISchemaValidator
{
    public async Task<SchemaValidationResult> ValidateAsync(
        object metadata, 
        string metadataType)
    {
        var schema = await GetSchemaAsync(metadataType);
        var metadataJson = JsonSerializer.Serialize(metadata);
        var errors = schema.Validate(metadataJson);
        
        return new SchemaValidationResult
        {
            IsValid = !errors.Any(),
            Errors = errors.Select(MapError).ToList()
        };
    }
}
```

**前端（TypeScript - Zod）**:
```typescript
export const EntityMetadataSchema = z.object({
  name: z.string().regex(/^[A-Z][a-zA-Z0-9]*$/),
  module: z.string().min(1),
  properties: z.array(PropertyMetadataSchema).default([])
})

export function validateEntityMetadata(data: unknown): EntityMetadata {
  return EntityMetadataSchema.parse(data)
}
```
