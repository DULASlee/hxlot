### 问题2：规则过于僵化（缺少灵活性）

```yaml
问题描述:
  - 所有任务都要求执行六阶段流程
  - 所有任务都要求15节点深度分析
  - 所有任务都要求业界搜索（5个）
  - 300行强制停止（无论任务类型）

实际情况:
  - 简单任务（修改变量名）不需要复杂流程
  - 紧急修复需要快速响应
  - 用户可能只想要快速迭代

建议:
  - 根据任务复杂度分级
  - 提供精简版和完整版流程
  - 给AI判断的灵活性
```

### 问题3：AI能力与规则要求不匹配

```yaml
规则要求AI做:
  ❌ 内部维护跨会话状态（代码行数计数器）
  ❌ 30分钟自动重新加载规则
  ❌ 实际运行Chrome DevTools进行性能测试
  ❌ 执行真实的用户体验测试

AI实际能力:
  ✅ 无状态（每次对话独立）
  ✅ 无法自主触发定时任务
  ✅ 无法运行浏览器
  ✅ 只能生成代码和提供建议

建议:
  - 明确区分AI职责和外部工具职责
  - 让AI专注做它擅长的事
  - 状态追踪由外部工具负责
```

### 问题4：优先级不清晰

```yaml
问题:
  - 10个文件都叫"铁律"

结果:
  - AI无法判断真正的优先级
  - 规则之间可能冲突
  - 无法灵活应对

建议:
  - P0: 阻断性（3-5条）

# AI编程核心原则（不可妥协的底线）

## P0 阻断性规则（违反则禁止提交）

### 1. 类型安全原则
- ✅ TypeScript编译0错误
- ❌ 严禁使用 as any / @ts-ignore
- 原因: 类型安全是TypeScript的核心价值
- 例外: 无
- 检测: npm run type-check

### 2. 架构完整性原则
- ✅ packages黑盒架构（无../、无@/引用）
- ✅ 依赖层级正确（shared→core→designer）
- 原因: 保证模块独立性和可维护性
- 例外: package内部可用相对路径
- 检测: grep -r "'../'" packages/ 和 grep -r "@/" packages/

### 3. 功能完整性原则
- ✅ 前后端链路完整（UI→API→DB）
- ❌ 严禁花瓶式实现（空方法、Mock数据）
- 原因: 企业级系统必须真实可用
- 例外: 明确标记@mock的测试数据
- 检测: 手动验证功能可用

### 4. Git安全原则
- ✅ 先pull后push
- ✅ 使用标准化脚本（git-safe-sync.ps1）
- 原因: 避免代码冲突和丢失
- 例外: 无
- 检测: Git操作规范检查

### 5. 代码保护原则
- ❌ AI无权删除任何代码（需用户确认）
- ✅ 优先注释代替删除
- 原因: 防止误删除和便于回滚
- 例外: 用户明确四次确认后
- 检测: 人工审查

## P1 重要性规则（应该遵循，偶尔例外需说明）

1. DRY原则：复用优先，避免重复
2. 架构先行：理解架构后再编码
3. 质量优先：95分质量标准
4. 性能达标：前端<2s，后端<500ms
5. 错误处理：完善的异常处理

## P2 建议性规则（优化方向，可灵活调整）

1. 代码注释：关键逻辑有注释
2. 测试覆盖：重要功能有测试
3. 性能优化：算法和数据结构优化
4. 用户体验：友好的提示和反馈
```

```markdown
# AI开发指南

## 任务分级响应

### Level 1: 微小任务（<20行代码）
示例: 修改变量名、添加注释、调整样式
流程:
  1. 快速分析（1分钟）
  2. 直接修改
  3. 简单验证（TypeScript检查）
不需要: 业界搜索、15节点分析、用户确认

### Level 2: 中等任务（20-200行）
示例: 添加新组件、修复BUG、优化功能
流程:
  1. 理解需求（2-3分钟）
  2. 检索现有实现（DRY原则）
  3. 设计方案（简要分析）
  4. 编码实现
  5. 质量检查
不需要: 完整15节点、等待用户确认每一步

### Level 3: 重大任务（>200行）
示例: 新功能模块、架构调整、大规模重构
流程:
  1. 深度分析（15节点）
  2. 业界搜索（2-3个关键问题）
  3. 方案对比（提供2-3个方案）
  4. 用户确认方案
  5. 分步实现（每300行检查一次）
  6. 完整测试

## 代码标准（精简版）

### TypeScript标准
- 命名: camelCase（变量）、PascalCase（类）、UPPER_SNAKE_CASE（常量）
- 类型: 100%类型安全，禁止any
- 导入: packages用@smartabp/，主应用用@/

### Vue3标准
- <script setup lang="ts">
- 组合式API
- 响应式数据: ref/reactive
- Props和Emits类型定义

### C#标准
- PascalCase命名
- async/await异步
- Repository模式
- DTO分离

## 质量检查（简化版）

### 编码中检查（每100行）
1. TypeScript类型检查
2. 重要逻辑有注释
3. 错误处理完善

### 阶段完成检查（每个功能）
1. TypeScript: npm run type-check (0错误)
2. ESLint: npm run lint (0错误)
3. 架构合规: 无../、无@/在packages
4. 功能验证: 手动测试功能可用

### Git提交前检查
1. 使用脚本: pwsh git-safe-sync.ps1 -AutoCommit
2. 验证: 本地=远程

## 开发流程（弹性版）

根据任务级别选择流程：
- 微小任务: 直接修改 → 检查 → 提交
- 中等任务: 分析 → 编码 → 检查 → 提交
- 重大任务: 深度分析 → 用户确认 → 分步实现 → 全面检查 → 提交
```
